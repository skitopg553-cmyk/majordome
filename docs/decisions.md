# Décisions d'architecture

Format : date — décision — pourquoi.

- 2026-10-15 — **PWA Next.js d'abord, pas d'app native.** Ruben connaît React/TS/Supabase/Vercel ; une PWA s'installe sur Android. Le natif (Expo) viendra seulement si Health Connect, le temps d'écran ou l'écoute en arrière-plan l'exigent.
- 2026-10-15 — **Un seul agent avec des outils, pas de multi-agents.** Moins cher, plus simple à déboguer. On découpera quand un vrai goulot apparaîtra.
- 2026-10-15 — **Routage de modèles :** Haiku 5.5 (tri, catégorisation), Sonnet 5.5 (raisonnement), code classique (calculs, règles, dates).
- 2026-10-15 — **Lecture seule partout** (mails, agenda, banque) au départ.
- 2026-10-15 — **Banque via import CSV** avant toute API d'agrégation.
- 2026-10-15 — **Phase 0 protégée par un code d'accès** (variable `MAJORDOME_ACCESS_CODE`) plutôt que Supabase Auth : plus simple pour démarrer, empêche qu'un inconnu consomme les crédits API. Remplacé par Supabase Auth en phase 1.
- 2026-10-15 — **Point de passage unique `src/lib/ai.ts`** pour tous les appels Claude : garantit la journalisation des coûts dans `ai_calls`.
- 2026-10-15 — **Fournisseur IA interchangeable** (`AI_PROVIDER` = `openai` ou `anthropic`). Démarrage sur les crédits OpenAI restants, bascule vers Claude ensuite en changeant une variable Vercel. Le code appelle des *niveaux* (`sonnet`/`haiku`), pas des modèles précis.
- 2026-10-15 — **Pas de Supabase Auth pour l'instant** : l'app est mono-utilisateur, le code d'accès suffit. À revoir seulement si l'app est ouverte à d'autres.
- 2026-10-15 — **Pas de table `goals`** : un objectif est une mémoire de catégorie `objectif`. Une table de moins.
- 2026-10-15 — **Contexte injecté plutôt qu'outils de lecture** : mémoires et tâches en cours sont ajoutées au prompt à chaque message (code), l'agent n'a des outils que pour écrire. Moins d'allers-retours, moins cher. À revoir si les volumes grossissent.
- 2026-10-15 — **Fonctions Vercel à Paris (`cdg1`, `vercel.json`)**, à côté de Supabase (eu-west-3). Le plan Hobby autorise une seule région, ça suffit.
- 2026-10-15 — **Streaming de la réponse** : `runAgent` streame chaque appel modèle (OpenAI et Claude) et transmet le texte via `onText`. Les outils restent exécutés entre deux appels. `ai_calls` est inséré via `after()` pour ne pas retarder la réponse.
- 2026-10-15 — **Table `messages`** pour l'historique du chat (30 derniers rechargés). « Nouvelle conversation » ne supprime rien : elle mémorise une date dans le navigateur et on ne réaffiche que ce qui suit.
- 2026-10-15 — **Direction design** : noir chaud `#12100d`, crème `#ece4d4`, un seul accent laiton `#b8955a`, Cormorant Garamond (titres) + Inter (texte), barre d'onglets en bas. Palette dans le `@theme` de `globals.css`.
- 2026-10-15 — **Ajout rapide de tâche sans IA** (`POST /api/tasks`), avec le même anti-doublon (`isSimilar`) que l'agent. Mises à jour optimistes côté écran.
- 2026-10-15 — **`react-markdown`** pour afficher les réponses (n'interprète pas le HTML : pas d'injection).
- 2026-10-15 — **Icônes PWA générées par Next (`ImageResponse`)** plutôt que des PNG à la main : aucune dépendance en plus, une seule source.
- 2026-10-15 — **Structure de l'app (remplace les onglets Chat / Tâches / Mémoire)** : très peu d'onglets, tout en 1-2 taps, inspiration Revolut. Barre du bas : Accueil | Planning | **Majordome (orbe central)** | Finances | Forme. Parler à Majordome *est* l'app : l'orbe est le personnage (états repos / écoute / réflexion / parole), le chat s'ouvre en plein écran par-dessus, un petit bouton clavier permet d'écrire. Mémoire & objectifs + Réglages sont derrière l'avatar en haut. Pas de page Mails : les mails seront lus en arrière-plan pour détecter les RDV (phase 2) et apparaîtront dans Planning.
- 2026-10-15 — **Planning = une seule timeline par jour** (tâches + RDV), avec ajout rapide de tâche sans IA.
- 2026-10-15 — **Voix avancée (exception à « une phase à la fois »)** : dictée via l'API Web Speech du navigateur et lecture via `speechSynthesis` (voix française). Gratuit, sans clé ni backend. Repli sur le clavier si le navigateur ne la gère pas. Demandé par Ruben, car la voix est le cœur de l'app. Whisper, le mot d'activation et le widget restent en phase 3.
- 2026-10-15 — **Coquilles** : les sections non codées (agenda, finances, forme) affichent leur mise en page finale avec des données fictives centralisées dans `src/lib/demo-data.ts`, sans backend ni table. Tout bloc fictif porte le bandeau « Aperçu — données fictives · phase X » (`DemoBanner`). Une page entièrement fictive a un bandeau en tête, un bloc fictif dans une page réelle a le sien, et un RDV fictif dans la timeline porte l'étiquette « fictif ».
- 2026-10-16 — **Nouvelle identité « majordome. »** (remplace laiton + serif) : fond `#050506`, surfaces `#111215`, **un seul accent fluo `#6CF2FF`**. Pas de violet ni de vert, sauf vert/rouge discrets pour les montants +/− (`pos`/`neg`). Police **Poppins** partout. Signature « majordome. » avec un point final lumineux (`Wordmark`). Le personnage Majordome = un gros point lumineux cyan (orbe). Ton : vouvoiement (voir la décision du 20/10 « majordome britannique »), français simple, aucun chiffre inventé.
- 2026-10-16 — **Accueil d'après la maquette Google Stitch** (`design/stitch/`, référence de mise en page, pas du code copié) : salutation + résumé du jour (calculé en code), puis les cartes prochain RDV, tâches du jour (réelles), solde avec mini-courbe, objectif avec photo, « Ta forme » (3 chiffres) et « À valider ». Supprimés de la maquette : le carré étoile, le bandeau « omniscient » et les CDN (Tailwind CDN, Material Symbols). Icônes en SVG inline.
- 2026-10-16 — **« À valider » remplace les « actions réglées en autonomie »** : Majordome *propose* (ex. ajouter un RDV trouvé dans un mail), Ruben valide ou refuse d'un tap. Rien n'est exécuté sans accord (cohérent avec la règle « lecture seule + confirmation »). Pour l'instant, propositions fictives et choix gardés en local.
- 2026-10-16 — **Objectifs : champ `image_url` prévu** dans le futur modèle de données (image de fond de la carte). Image fixe `/public/objectif.jpg` (copiée depuis la maquette, pour ne pas dépendre d'un lien googleusercontent qui expire). Rien d'autre n'est codé.
- 2026-10-15 — **Le dépôt est la source de vérité** entre le chat (planification) et Claude Code (construction) : roadmap et décisions vivent ici.
- 2026-10-16 — **Ton des budgets : neutre.** Un budget dépassé s'affiche en gris avec « Au-dessus du budget de X € », jamais en rouge (l'app ne doit pas culpabiliser). Le rouge/vert ne servent qu'aux montants +/−.
- 2026-10-16 — **Chat vocal éphémère :** après une demande faite à la voix, le chat se referme 3 s après la fin de la réponse lue ; toucher l'écran annule la fermeture.
- 2026-10-16 — **L'IA est le point d'entrée de toute l'app.** Outils ajoutés (`src/lib/life-tools.ts`) : `log_workout`, `log_sleep`, `log_steps`, `set_budget`, `add_transaction`. Règles : ce qui est déjà fait va dans Forme / Finances, jamais dans les tâches ; l'IA lit la section « Vie de Ruben » (ce qui est déjà noté) avant d'écrire et ne note jamais deux fois ; au plus une question courte après chaque action ; validation en code (`src/lib/life.ts`, pas de date future) ; écriture seulement par ajout ou remplacement, **aucune suppression par l'IA** (Ruben supprime dans l'app, donc c'est réversible). Pas d'écriture dans l'agenda tant qu'il n'est pas connecté (phase 2) : elle propose une tâche avec une heure.
- 2026-10-16 — **Table `steps_logs`** (migration 0008) : pas du jour, un total par date ; mode « add » (en plus) ou « set » (remplace).
- 2026-10-16 — **Objectifs d'épargne éditables** : outil IA `set_goal` + formulaire « Nouvel objectif / Modifier » dans Finances (même nom = mise à jour, via `saveGoal`). Un vrai objectif n'utilise jamais la photo d'exemple : dégradé par défaut aux couleurs de l'app (`.goal-default`) tant que Ruben n'a pas choisi d'image (`image_url`, pas encore de sélecteur).
- 2026-10-16 — **Import Revolut + Excel.** Format Revolut reconnu automatiquement (colonnes Completed Date / Description / Amount / Fee / State) : date = Completed Date, montant = Amount − Fee, seules les lignes COMPLETED en EUR sont importées (jamais de conversion de devise : aucun taux inventé). Les .xlsx sont lus dans le navigateur par `read-excel-file` (chargé à la demande, une seule dépendance : fflate, aucune alerte `npm audit`) puis convertis en CSV : un seul chemin d'import. L'ancien .xls n'est pas géré (message clair).
- 2026-10-16 — **Connexion bancaire : Enable Banking, mode restreint, lecture seule.** Agrégateur PSD2 (API `api.enablebanking.com`) pour lire en direct les comptes Revolut de Ruben et remplir `transactions` + le solde. Choix : (1) **mode restreint** : l'app n'accède qu'aux comptes que Ruben a lui-même autorisés (pas d'usage commercial, cohérent avec « usage perso d'abord ») ; (2) **lecture seule stricte** : seuls les appels `GET` de données et la création de session sont utilisés, jamais d'initiation de paiement ; (3) **JWT RS256 signé avec le module `crypto` natif** (pas de dépendance `jose`), clé et App ID uniquement dans les variables d'environnement (`ENABLE_BANKING_APP_ID`, `ENABLE_BANKING_PRIVATE_KEY`), jamais loggés ; (4) le consentement PSD2 est **limité dans le temps** (90 jours max) : l'app affiche un avertissement avant l'expiration et il faut reconnecter ; (5) l'import CSV / Excel reste le plan B ; (6) les messages d'erreur de l'API sont affichés tels quels (usage perso, utile pour diagnostiquer).
- 2026-10-16 — **Fiabilité de l'agent : trois filets.** (1) Les ordres explicites (« retiens que… », « n'oublie pas… », « objectif 3000 € pour… », « mon objectif est… ») sont reconnus et exécutés **par le code avant le modèle** (`src/lib/intents.ts`) ; le modèle reçoit « Déjà fait pour Ruben dans ce message » et ne fait que confirmer. Les phrases ambiguës (« je veux… ») restent au modèle. (2) Consignes durcies (`src/lib/instructions.ts`) : interdiction de dire « j'ai noté » sans outil appelé. (3) **Alerte automatique** si la réponse affirme avoir enregistré quelque chose alors qu'aucun outil n'a été appelé (constaté en vrai : « J'ai noté ton objectif » sans rien d'écrit) ; l'alerte est aussi gardée dans l'historique pour ne pas induire le modèle en erreur au message suivant. Un souvenir similaire n'est jamais enregistré deux fois.
- 2026-10-16 (soir) — **Tout est pilotable à la voix, y compris supprimer.** Revient sur « aucune suppression par l'IA » : l'outil `delete_entry` supprime UNIQUEMENT sur demande claire de Ruben (consignes dans `instructions.ts`), pour tâche, objectif, budget, opération, séance, nuit, pas, repas, temps d'écran. Garde-fou : le bouton **Annuler** (10 s) recrée la ligne (`op: "insert"` étendu à toutes les tables de la liste blanche `RESTORABLE`, mêmes colonnes autorisées). Ajoutés : `add_to_goal`, `update_transaction`, `update_workout`, `update_memory`, `set_setting` (seul réglage : lecture à voix haute, stocké dans le navigateur → envoyé à l'écran par un second « trailer » `U+001D` dans le flux, appliqué côté appareil).
- 2026-10-16 (soir) — **Épargne calculée en code** (`src/lib/finance/savings.ts`) : sur les 3 derniers mois COMPLETS, Libre = revenus moyens − charges fixes − dépenses variables (médiane mensuelle) − 10 % des revenus. Charge fixe = même libellé (chiffres et dates ignorés) dans ≥ 2 mois avec montants à ±15 % de leur médiane. « Engagé » = charges fixes ; « Mis de côté » = total des objectifs. Mensualité nécessaire = (cible − épargné) ÷ mois restants (échéance lue dans le texte libre « Juin », « juin 2027 » ; sans année = prochaine occurrence). Un objectif sans date compréhensible n'est pas comparé.
- 2026-10-16 (soir) — **Nutrition : le LLM comprend, le code calcule.** `log_food` reçoit aliment + quantité + unité ; kcal et macros viennent de `src/lib/nutrition/foods.json` (~250 aliments courants, pour 100 g). **Source : table Ciqual de l'ANSES (ciqual.anses.fr, licence ouverte Etalab 2.0).** ⚠️ Les valeurs ont été recopiées de mémoire et arrondies, sans téléchargement du fichier officiel (session autonome) : bon ordre de grandeur, à vérifier ligne par ligne avant de s'y fier (un test vérifie seulement la cohérence kcal ≈ 4P + 4G + 9L). Aliment inconnu → estimation du LLM pour 100 g, refusée si absurde ou incohérente, enregistrée avec `estimated = 1` et affichée « estimé ». Un aliment connu de la table l'emporte toujours sur une estimation. Pas de nouvelle dépendance. Riz/pâtes sans précision = cuits (le plus courant) ; 1 ml = 1 g ; cuillère à soupe 15 g, à café 5 g.
- 2026-10-16 (soir) — **Temps d'écran** : une PWA ne peut pas le lire → saisie (voix, bouton), capture « Bien-être numérique » lue par vision (`/api/screen-time/read`, qui ne sauvegarde RIEN : l'écran confirme, puis `POST /api/screen-time`), ou Tasker (`docs/temps-ecran.md`). `runAgent` accepte maintenant des images (data URL) sur les deux fournisseurs ; l'appel est journalisé comme tous les autres. Tendance : moyenne des 7 derniers jours vs les 7 précédents (jours renseignés) ; baisse = couleur d'accent, hausse = gris, jamais de rouge.
- 2026-10-16 (soir) — **Limite d'essais du code d'accès** (`src/lib/rate-limit.ts`, branchée dans `denied`) : 5 mauvais codes depuis la même IP (`x-forwarded-for`) → 10 min d'attente, même avec le bon code pendant l'attente. Un bon code remet le compteur à zéro ; un en-tête vide n'est pas compté. **En mémoire** (pas de table, rien à migrer) : chaque instance Vercel a son compteur et un redéploiement le vide, donc la protection est partielle sur plusieurs instances (limite notée dans le code). Pendant l'attente l'écran affiche « Code d'accès incorrect » (la route répond 401).
- 2026-10-16 (retouches) — **Temps d'écran : retour à l'aperçu fictif.** Retirés : lecture de capture par vision (route `/api/screen-time/read`, support d'images dans `runAgent`), outil IA `log_screen_time`, carte réelle. Gardés : table `screen_time_logs`, route `POST /api/screen-time` (Tasker), calculs `src/lib/screen-time.ts` (tendance 7 j vs 7 j, prêts mais non branchés).
- 2026-10-16 (retouches) — **Agenda ≠ tâche, règle en code sans migration** (`isAgenda` dans `src/lib/planning.ts`) : une échéance avec une heure précise (≠ 00:00 à Paris) est un élément d'agenda → Planning seulement ; sans heure (00:00 ou sans date) → tâche → Accueil seulement. Une seule table `tasks`. L'IA met minuit pour « demain » sans heure et n'invente jamais d'heure ; seuls les éléments d'agenda déclenchent un rappel.
- 2026-10-16 (retouches) — **Table nutritionnelle : valeurs officielles Ciqual 2020** pour 138 des 261 aliments (fichier XML de l'ANSES, `scripts/ciqual-build.mjs` + `scripts/ciqual-codes.txt`, appariement par code vérifié à la main ; le code Ciqual est la 7e valeur de chaque ligne de `foods.json`). Les 123 autres gardent leurs anciennes valeurs approximatives (aucun appariement fiable trouvé, ex. fruits courants). Remplace la mention « recopiées de mémoire » ci-dessus pour les 138 premiers.
- 2026-10-16 (weekend) — **Table nutritionnelle : 166 aliments sur 261 lus dans Ciqual 2020** (au lieu de 138). Protéines : facteur de Jones, à défaut N × 6,25 ; énergie : règlement UE, à défaut Jones avec fibres, à défaut calculée par les facteurs d'Atwater (4/4/9) ; un seul macro absent est mis à 0 si l'énergie colle. Les 95 autres gardent des valeurs approchées (pas de code Ciqual sûr).

- 2026-10-18 (lundi) — **La mascotte « majordome. » remplace l'orbe, 100 % en CSS + JS maison** : deux yeux blancs arrondis, deux « paupières » de la couleur du fond posées dessus (celle du haut penchable = sourcils, celle du bas arrondie = joues). Aucune librairie 3D ni dépendance. Un seul composant `<Majordome size>` (`src/app/majordome.tsx`), un seul état partagé (`mascot-engine.ts` : regard, humeur, voix) animé par UNE boucle requestAnimationFrame qui modifie directement le style des yeux (pas de re-rendu React 60 fois par seconde). La partie « vivante » (regard qui suit le doigt et le focus, dérive au repos, clignements aléatoires, sommeil après 60 s) est du code pur : zéro IA, zéro coût. `prefers-reduced-motion` : plus de suivi ni de dérive, seulement les clignements. Les valeurs des émotions et l'interpolation sont dans `src/lib/mascot.ts`, testées.
- 2026-10-18 (lundi) — **Humeur de la mascotte via une balise `@mood:xxx` en 1re ligne de la réponse du modèle** (neutral, happy, sad, angry, surprised, focus) : aucun appel IA en plus. Le serveur retire la balise du flux (classe `MoodStripper`, qui gère une balise coupée entre deux morceaux), avant l'affichage, la lecture vocale et l'enregistrement dans `messages`, et envoie l'humeur en tête du flux (entre deux U+001F). Absente ou inconnue = neutral. L'humeur reste 5 s. `angry` seulement si on lui parle mal ; jamais d'humeur qui culpabilise. Réactions du code seul : tâche cochée → happy, dépense inhabituelle → surprised, erreur réseau → sad (2 s).
- 2026-10-18 (lundi) — **Tâches planifiées côté serveur avec Supabase pg_cron + pg_net, pas Vercel Cron** (le plan gratuit de Vercel ne lance un cron qu'une fois par jour : trop imprécis pour des rappels). Chaque minute : `/api/push/send` (rappels dus, 5 min avant). Chaque jour à 4 h (Paris) : `/api/cron/recurring` crée les tâches récurrentes du jour. pg_cron compte en UTC : le job tourne à 2 h et 3 h UTC et la route ne fait quelque chose que s'il est 4 h à Paris. Les deux routes sont protégées par `x-cron-secret` (secret dans Vercel ET dans le Vault Supabase), comparé en temps constant. Pas de tâche planifiée Windows.
- 2026-10-18 (lundi) — **Réveils et minuteurs par lien Android** : une app web ne peut pas créer un réveil toute seule. Les outils `set_alarm` / `set_timer` calculent l'heure en code et renvoient une carte avec un VRAI lien `intent:#Intent;action=android.intent.action.SET_ALARM;…` qui ouvre l'Horloge déjà remplie ; Ruben valide d'un tap (Chrome bloque une ouverture qui ne vient pas d'un tap). Le libellé est encodé ; seuls les liens SET_ALARM / SET_TIMER sont acceptés côté écran. À tester sur téléphone : on ne sait pas si l'app installée laisse passer ces liens.
- 2026-10-18 (lundi) — **Google : mails → rendez-vous SANS écriture chez Google.** Lecture seule (Agenda + Gmail). Mails non lus des 48 h → pré-filtre en code → Haiku sur les seuls candidats (20 par jour au plus, journalisé dans `ai_calls`) → date et heure vérifiées et calculées en code → pas de proposition si un événement existe déjà à ±45 min. Proposition = carte avec « Ajouter à mon planning » (tâche majordome), « Ajouter à Google Agenda » (lien `calendar.google.com/calendar/render?action=TEMPLATE…` : c'est Google qui écrit, après le tap de Ruben) et « Ignorer ». On ne stocke jamais le contenu des mails : seulement l'identifiant et ce qui a été extrait (table `mail_suggestions`). Les tables Google sont fermées (RLS sans règle + droits retirés à anon / authenticated). ⚠️ Le contenu des mails candidats (≤ 2 000 caractères) est envoyé au fournisseur d'IA pour l'extraction. Jeton expiré (`invalid_grant`, fréquent en mode Test : ~7 jours) → carte « Reconnecter Google », jamais un écran cassé.
- 2026-10-18 (voix-android) — **Voix cloud avec repli sur le téléphone, jamais un point de panne.** Moteur retenu pour comparer : OpenAI `gpt-4o-mini-tts` (la clé existe déjà), avec une consigne de ton (voix posée, chaleureuse, rythme naturel). Gemini et ElevenLabs seulement quand une clé est donnée (pas de code écrit pour des services qu'on ne peut pas tester). Route `/api/tts` protégée par le code d'accès : texte nettoyé côté serveur (`speech-text.ts` : balise `@mood:`, markdown, emojis, heures/euros/nombres en toutes lettres), plafond de caractères par jour (`VOICE_MAX_CHARS_PER_DAY`, défaut 8 000 ≈ 0,13 $) calculé sur `ai_calls` (purpose « tts », `input_tokens` = nombre de caractères), cache en mémoire des phrases de moins de 80 caractères, au moindre souci → `{ fallback: true }` et l'écran lit avec la voix du téléphone sans message d'erreur (`speakWithFallback`). **Intégration dans le chat volontairement NON faite** : Ruben choisit d'abord à l'oreille sur `/voix-test`.
- 2026-10-18 (voix-android) — **Réveils : la confirmation et la carte viennent du CODE, pas de l'IA.** Cause du bug « carte une fois sur trois » : le modèle (gpt-4o-mini) recopiait la phrase « Touche le bouton pour le créer » donnée dans ses consignes sans appeler l'outil. Correctif : `alarm-intent.ts` reconnaît la phrase (heures en chiffres ou en lettres, « demain », « dans 20 minutes », durées, libellé), exécute l'outil et écrit la phrase (`alarm-speech.ts`) sans appeler le modèle ; consigne au modèle : répondre seulement « OK » après l'outil, ne jamais dire « c'est fait » / « touche le bouton » ; garde-fou : si la réponse parle de bouton sans carte envoyée, un avertissement est ajouté. Principe général : **un ordre clair se traite en code d'abord, l'IA en repli** (déjà vrai pour « retiens que… »).
- 2026-10-18 (voix-android) — **Coque Android avec Capacitor, dossier `android/` séparé** (son propre `package.json`, rien ajouté aux dépendances du site). La coque charge l'adresse de production (`server.url`), pas d'export statique, navigation limitée à notre domaine (`allowNavigation`). Plugin `Alarm` natif (`setAlarm`, `setTimer`, `EXTRA_SKIP_UI = true`, `resolveActivity`, `<queries>` obligatoire sous Android 11+). Dans la coque (`Capacitor.isNativePlatform()`), la carte règle l'Horloge toute seule et la phrase de confirmation est générée à partir de l'heure réellement envoyée ; en cas d'erreur : « Je n'ai pas réussi à régler le réveil » + bouton de repli. **Écart avec la demande : plugin écrit en Java, pas en Kotlin** : le modèle Capacitor est en Java ; Kotlin demande d'ajouter et d'accorder des versions de plugins Gradle, et je ne peux pas compiler ici (Android Studio non installé) : je réduis ce qui peut casser. Même effet, ~60 lignes ; passage à Kotlin possible plus tard. APK debug seulement, aucune clé de signature dans git. Aucune dépendance Capacitor dans le site : le code web appelle `window.Capacitor.Plugins.Alarm` quand il existe.
- 2026-10-18 (voix-android) — **Audit produit publié (`docs/audit.md`)**, sans code modifié : constat principal = l'usage quotidien n'a pas commencé (25 messages en 3 jours), les rappels sont éteints, le prompt fixe pèse ~5 100 tokens par appel (outils par intention + cache + petit modèle par défaut = condition d'un abonnement à 10-15 €), la sécurité repose sur un code partagé (bloquant pour vendre).

- 2026-10-19 (ménage) — **Fin des données fictives.** `src/lib/demo-data.ts` et `DemoBanner` supprimés : Accueil, Planning, Finances et Forme n'affichent plus que du réel ; sans données, une invitation honnête (« Ton solde apparaîtra ici », « Pas encore d'objectif ») ou un message « indisponible + Réessayer ».
